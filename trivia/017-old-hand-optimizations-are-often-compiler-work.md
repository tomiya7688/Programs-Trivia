# #017 昔の高速化テクニックってな、今はコンパイラに任せた方がいいことが多いんだぜ

昔の高速化テクニックを見ると、

```text
for文を手で4回分に展開するんだぜ
割り算を掛け算にするんだぜ
平方根を近似式にするんだぜ
sinやcosを近似多項式にするんだぜ
```

みたいなのが山ほど出てくるんだぜ。

もちろん、昔はちゃんと意味があったんだぜ。

でもな。

**今の一般的なプログラムでは、こういう低レベル最適化を人間が先回りして書く意味は昔よりかなり小さくなったんだぜ。**

理由は単純なんだぜ。

> **コンパイラとCPUがめちゃくちゃ賢くなったんだぜ。**

### for文を手で展開する、ってやつなんだぜ

例えば、

```c
for (int i = 0; i < n; i++) {
    a[i] += b[i];
}
```

があるんだぜ。

昔なら、

```c
for (int i = 0; i < n; i += 4) {
    a[i + 0] += b[i + 0];
    a[i + 1] += b[i + 1];
    a[i + 2] += b[i + 2];
    a[i + 3] += b[i + 3];
}
```

みたいに書いて、

> **ループの判定回数を減らすんだぜ。**

とやることがあったんだぜ。

これが **loop unrolling** なんだぜ。

でも今のLLVMやGCCは、こんなの自分でやるんだぜ。

LLVMのLoop Vectorizerは、

```text
何個まとめてSIMDにするんだぜ
何回unrollするんだぜ
レジスタは足りるんだぜ
コードサイズは増えすぎないんだぜ
```

までコストモデルで判断するんだぜ。

GCCも `-O3` では、

```text
loop unroll and jam
loop peeling
loop interchange
loop vectorization
SLP vectorization
```

みたいな最適化を普通に持ってるんだぜ。

つまり人間が、

> **4回展開した方が速そうなんだぜ。**

と決め打ちするより、

> **このCPUなら何回展開するのが得なんだぜ？**

をコンパイラに決めさせた方がいいことが多いんだぜ。

### 展開すれば展開するほど速いわけじゃないんだぜ

ここが大事なんだぜ。

for文を展開すると、

```text
分岐が減るんだぜ
並列に実行しやすくなるんだぜ
```

という利点があるんだぜ。

でも同時に、

```text
コードが大きくなるんだぜ
命令キャッシュを食うんだぜ
レジスタをたくさん使うんだぜ
```

という欠点もあるんだぜ。

GCCのマニュアルにも、ループ展開はコードを大きくし、

> **速くなることもあれば、ならないこともあるんだぜ。**

という趣旨で書かれてるんだぜ。

さらに `-funroll-all-loops` みたいに何でも展開すると、

> **普通はむしろ遅くなるんだぜ。**

とまで書いてあるんだぜ。

つまり、

**展開すること自体が最適化なんじゃないんだぜ。**

**そのCPUとそのコードで得する量だけ展開するのが最適化なんだぜ。**

### ベクトル演算を近似式にするのも昔の定番なんだぜ

3Dゲームや数値計算では、

```text
sqrtなんだぜ
1 / sqrtなんだぜ
sinなんだぜ
cosなんだぜ
expなんだぜ
logなんだぜ
```

みたいな計算が大量に出るんだぜ。

昔はこういう計算が高かったから、

```text
平方根を近似するんだぜ
逆平方根をビット演算で近似するんだぜ
三角関数を多項式で近似するんだぜ
```

みたいな技が重要だったんだぜ。

有名な **fast inverse square root** なんかもこの系統なんだぜ。

精度を少し捨てて、

> **だいたい合ってればいいから、とにかく速くするんだぜ。**

だったんだぜ。

### 今は「近似していいんだぜ」までコンパイラに伝えられるんだぜ

今のClangには `-ffast-math` や `-fapprox-func` があるんだぜ。

`-fapprox-func` を許可すると、

```text
sqrt
log
pow
```

みたいな関数を、厳密には完全一致しないけど高速な計算へ置き換えていいんだぜ。

`-freciprocal-math` なら、

```text
割り算
    ↓
逆数を掛ける
```

みたいな変換も許可できるんだぜ。

つまり昔なら人間が、

> **ここは精度を少し捨ててこの近似式を使うんだぜ。**

とソースコードへ埋め込んでいた判断を、

> **この範囲なら近似していいんだぜ。あとはターゲットCPUに合わせて頼むんだぜ。**

とコンパイラに渡せるんだぜ。

### 数学ライブラリの中の人が本気で最適化してるんだぜ

しかも自分で近似式を書く相手は、コンパイラだけじゃないんだぜ。

Intel oneMKLみたいなライブラリには、

```text
sqrtなんだぜ
inverse sqrtなんだぜ
sinなんだぜ
cosなんだぜ
expなんだぜ
logなんだぜ
```

をベクトル単位で計算する、高度に最適化された実装があるんだぜ。

精度モードまで選べるんだぜ。

つまり自分で、

```c
// 俺が考えた高速sqrtなんだぜ
```

を書く前に、

> **そのCPUを知り尽くした人が作った実装、もうあるんじゃないんだぜ？**

を考えた方がいいんだぜ。

### CPUそのものにも専用命令があるんだぜ

昔は、

> **この計算は命令が高いから、別の式へ変形するんだぜ。**

という発想が重要だったんだぜ。

でも現代CPUには、

```text
SIMDなんだぜ
FMAなんだぜ
vector sqrtなんだぜ
reciprocal系の命令なんだぜ
```

みたいな専用機能があるんだぜ。

しかもCPUごとに、

```text
この命令は速いんだぜ
この命令は遅いんだぜ
この幅のSIMDが使えるんだぜ
```

が違うんだぜ。

だから人間がソースコード上で、

> **この式の方が絶対速いんだぜ。**

と思っても、別のCPUでは逆転することがあるんだぜ。

**ソースコードの見た目だけでは、もう機械語の速さを読み切れないんだぜ。**

### むしろ素直に書いた方が最適化しやすいこともあるんだぜ

コンパイラは典型的な形を見つけるのが得意なんだぜ。

例えば、

```c
for (int i = 0; i < n; i++) {
    out[i] = a[i] + b[i];
}
```

みたいな素直なコードなら、

> **これvectorizeできるんだぜ。**

と判断しやすいんだぜ。

でも人間が先回りして、

```text
特殊なビット演算なんだぜ
妙な分岐なんだぜ
手書きの展開なんだぜ
独自の近似式なんだぜ
```

を入れると、

**コンパイラが元の意味を認識しにくくなることもあるんだぜ。**

人間が最適化したつもりで、

> **コンパイラの最適化を邪魔したんだぜ。**

になることもあるんだぜ。

### じゃあ手動最適化はもう要らないんだぜ？

そこまで言ったら嘘なんだぜ。

今でも、

```text
ゲームエンジンなんだぜ
OSなんだぜ
動画codecなんだぜ
データベースなんだぜ
暗号なんだぜ
HPCなんだぜ
GPU kernelなんだぜ
組み込みなんだぜ
DSPなんだぜ
```

みたいな世界では、手動最適化が重要なんだぜ。

SIMD intrinsicを書くこともあるんだぜ。

アセンブリを書くこともあるんだぜ。

近似式を自分で選ぶこともあるんだぜ。

メモリ配置を1バイト単位で気にすることもあるんだぜ。

でも順番が違うんだぜ。

昔みたいに、

> **速そうだから最初からfor文を展開するんだぜ。**

じゃないんだぜ。

```text
普通に書くんだぜ
    ↓
最適化付きでコンパイルするんだぜ
    ↓
プロファイルするんだぜ
    ↓
生成された機械語を見るんだぜ
    ↓
本当に遅いところだけ手で触るんだぜ
```

なんだぜ。

### 近似は「高速化」じゃなくて仕様変更でもあるんだぜ

近似式については、もう一個大事なんだぜ。

```text
正確なsqrt
```

を、

```text
だいたいsqrt
```

に変えるのは、単なる最適化じゃないんだぜ。

**答えが変わるんだぜ。**

Clangの `-ffast-math` も、

```text
NaNを無視していいんだぜ
Infinityを無視していいんだぜ
+0と-0を同じように扱っていいんだぜ
結合法則っぽく並べ替えていいんだぜ
```

みたいな、かなり強い仮定を許すんだぜ。

速くなる代わりに、IEEE 754どおりの厳密な挙動から離れることがあるんだぜ。

だから、

> **近似式の方が速いから使うんだぜ。**

じゃなくて、

> **この用途では、この誤差を許していいんだぜ。**

が先なんだぜ。

### だからなんだぜ

昔の高速化本を見ると、

```text
for文を展開するんだぜ
式を手で変形するんだぜ
近似式にするんだぜ
分岐をビット演算にするんだぜ
```

みたいなテクニックがたくさん出てくるんだぜ。

今でも原理としては面白いし、必要な場所では使うんだぜ。

でも普通のコードで最初からやるものではなくなってきたんだぜ。

**今は人間がCPUの代わりに最適化するんじゃないんだぜ。**

**人間は意図を分かりやすく書いて、コンパイラに最適化させるんだぜ。**

そして本当に足りなかったところだけ、人間が最後に手を出すんだぜ。

> **最適化は、賢そうなコードを書くことじゃないんだぜ。**
>
> **測って、本当に必要なところだけ速くすることなんだぜ。**
