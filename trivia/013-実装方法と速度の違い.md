# #013 同じことを書くにも、速さは全然違うんだぜ

プログラムを書いてると、

```text
動けば同じなんだぜ
```

に見えるコードがあるんだぜ。

でもな。

**同じ結果を出すコードでも、書き方やデータ構造で速度が何倍も何百倍も変わることがあるんだぜ。**

今回はこの環境の **CPython 3.13.5** で `timeit` を使って測った一例なんだぜ。

数字はCPUやPythonのバージョン、入力サイズで変わるんだぜ。

だから、

> **この倍率が世界共通なんだぜ。**

ではないんだぜ。

でも、

> **同じ意味でも、実装の仕方でこんなに差が出るんだぜ。**

を見るには十分なんだぜ。

### 足し算するなら、手で回すよりsumの方が速かったんだぜ

10万個の整数を足すんだぜ。

まず普通に書くんだぜ。

```python
s = 0

for i in range(100_000):
    s += i
```

この環境では、だいたい **3.88 ms** だったんだぜ。

一方で、

```python
sum(range(100_000))
```

なら、だいたい **1.55 ms** だったんだぜ。

つまり手書きループの方が、

> **約2.5倍遅かったんだぜ。**

なんだぜ。

どっちもやってることは、

```text
0から99999まで足すんだぜ
```

なんだぜ。

でもPython側で何度もループを回すより、組み込み関数にまとめて仕事を渡した方が速くなることがあるんだぜ。

しかも、

```python
sum(values)
```

の方が何をしたいかも一発で分かるんだぜ。

**速くて短いこともあるんだぜ。**

### 文字列をつなぐならjoinが10倍くらい速かったんだぜ

1万個の文字列をつなぐんだぜ。

こう書けるんだぜ。

```python
s = ""

for part in parts:
    s += part
```

この環境では、だいたい **0.589 ms** だったんだぜ。

でも、

```python
"".join(parts)
```

なら、だいたい **0.056 ms** だったんだぜ。

つまり `+=` で繰り返しつなぐ方が、

> **約10.4倍遅かったんだぜ。**

なんだぜ。

これも結果は同じ文字列なんだぜ。

でも `join` は、

> **最初から全部まとめてつなぐ仕事なんだぜ。**

と処理系に伝えられるんだぜ。

「何をしたいか」を高いレベルで書いた方が、処理系が効率よくやれることもあるんだぜ。

### 探すだけで2700倍くらい差が出たんだぜ

今度は、

```text
0から9999まで入ったデータから9999を探すんだぜ
```

をやるんだぜ。

listなら、

```python
xs = list(range(10_000))

9999 in xs
```

なんだぜ。

この環境では1回あたり、だいたい **58.6 μs** だったんだぜ。

一方でsetなら、

```python
xs = set(range(10_000))

9999 in xs
```

は、だいたい **0.021 μs** だったんだぜ。

この実測ではlistの検索が、

> **約2700倍遅かったんだぜ。**

なんだぜ。

急に桁がおかしいんだぜ。

理由は単純なんだぜ。

listは基本的に、

```text
これなんだぜ？
違うんだぜ
次なんだぜ？
違うんだぜ
次なんだぜ？
...
```

と順番に探すんだぜ。

setはハッシュを使って、

> **たぶんこの辺にあるんだぜ。**

とかなり直接的に探しに行けるんだぜ。

**アルゴリズムやデータ構造の違いは、細かい書き方の工夫なんか吹き飛ばすことがあるんだぜ。**

### じゃあ全部setにすればいいんだぜ？

そうはならないんだぜ。

setには、

```text
重複を持たないんだぜ
インデックスで何番目とは取れないんだぜ
listとは意味が違うんだぜ
追加のメモリも使うんだぜ
```

という性質があるんだぜ。

しかも今回の測定では、**setを作る時間は検索時間に含めてない**んだぜ。

1回しか検索しないのに、

```python
9999 in set(xs)
```

と毎回setを作ってたら、その準備の方が高くつくこともあるんだぜ。

つまり、

> **検索だけ見たら2700倍速いんだぜ。**

と、

> **プログラム全体が2700倍速くなるんだぜ。**

は全然違う話なんだぜ。

### ベンチマークの数字だけ見ると簡単に騙されるんだぜ

例えば、

```text
AはBより10倍速いんだぜ
```

と言われると、Bを全部書き換えたくなるんだぜ。

でも元の処理が、

```text
1回 0.05 ms
```

しか使ってないなら、10倍速くしても体感できないかもしれないんだぜ。

逆に、

```text
毎秒100万回呼ばれるんだぜ
```

なら、小さな差でも巨大になるんだぜ。

大事なのは、

```text
何回呼ばれるんだぜ
どれくらいのデータなんだぜ
全体時間の何％なんだぜ
メモリはどれくらい増えるんだぜ
コードは読みにくくならないんだぜ
```

なんだぜ。

### 読みやすいコードを壊して1μsを取りに行くこともできるんだぜ

例えば、

```python
result = some_clear_function(data)
```

を、

```text
関数呼び出しを消すんだぜ
変数を使い回すんだぜ
条件分岐を展開するんだぜ
読みにくい最適化を山ほど入れるんだぜ
```

にすれば少し速くなることはあるんだぜ。

でも半年後、

> **これ何してるんだぜ？**

となったら、人間の時間を大量に失うんだぜ。

コンピュータの1ミリ秒を救うために、

**プログラマの1時間を燃やしたら得なのか**

は考えないといけないんだぜ。

### まず測るんだぜ

だから速度が気になったら、

> **たぶんここが遅いんだぜ。**

で書き換え始めるんじゃないんだぜ。

まず測るんだぜ。

Pythonなら `timeit` みたいな道具があるんだぜ。

本物のアプリならprofilerを使って、

```text
本当に遅い場所はどこなんだぜ
```

を見るんだぜ。

速くするなら、

**一番時間を食ってるところからなんだぜ。**

### だからなんだぜ

コードには、

```text
実行速度なんだぜ
メモリ使用量なんだぜ
読みやすさなんだぜ
書きやすさなんだぜ
保守しやすさなんだぜ
バグりにくさなんだぜ
```

があるんだぜ。

速度は大事なんだぜ。

遅すぎたら使い物にならないんだぜ。

でも、

> **一番速いコードが、一番いいコードなんだぜ。**

とは限らないんだぜ。

必要なだけ速くて、意味が分かって、壊しにくい。

その方がいい場面はいくらでもあるんだぜ。

**早ければいいってもんじゃないぜ。**
