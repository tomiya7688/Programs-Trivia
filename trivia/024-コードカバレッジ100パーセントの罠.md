# #024 コードカバレッジ100%ってな、安心どころか危険なこともあるんだぜ

テストの話をすると、

```text
coverage 80%なんだぜ
coverage 95%なんだぜ
coverage 100%なんだぜ
```

みたいな数字が出てくるんだぜ。

すると当然、

> **100%が一番いいんだぜ。**

と思いたくなるんだぜ。

でもな。

**コードカバレッジ100%は、「全部ちゃんとテストできた」という意味じゃないんだぜ。**

場合によっては、

> **100%にしたから安心なんだぜ。**

という気持ちの方が危険なんだぜ。

## coverageが測ってるのは「通ったか」なんだぜ

普通のline coverageは、

> **その行をテスト中に一回でも実行したんだぜ？**

を数えてるんだぜ。

例えば、

```python
def divide(a, b):
    return a / b
```

を、

```python
assert divide(10, 2) == 5
```

でテストしたんだぜ。

これで関数の行は全部通るんだぜ。

だからline coverageは100%になり得るんだぜ。

でも、

```python
divide(10, 0)
```

は試してないんだぜ。

つまり、

> **行は全部通ったんだぜ。**
>
> **入力パターンは全部試したんだぜ。**

は別なんだぜ。

GoogleのTesting Blogも、high coverageはwell-testedであるための必要条件にはなり得ても、十分条件ではないと説明してるんだぜ。

## branchを通してないのに100%になることもあるんだぜ

例えば、

```python
def f(x):
    if x:
        y = 10
    return y
```

があるんだぜ。

```python
f(True)
```

だけ実行したんだぜ。

行としては全部通ったんだぜ。

でも、

```text
x = False
```

の経路は通ってないんだぜ。

coverage.pyも、普通のstatement coverageとは別に **branch coverage** を用意してるんだぜ。

理由はそのまんまで、

> **行を通しただけでは、条件分岐の両側を通したとは限らないんだぜ。**

からなんだぜ。

つまり100% line coverageですら、

**まだ「全部の動き」を見たわけじゃないんだぜ。**

## 100%にするために「冗長なテスト」を消すと危ないんだぜ

ここが一番面白いところなんだぜ。

coverageだけを見ると、

```text
このテストも同じ行を通ってるんだぜ
じゃあいらないんだぜ
```

って思うことがあるんだぜ。

例えば、

```python
def handle(code):
    if code == "fatal":
        return "stop"
    else:
        return "ok"
```

があるんだぜ。

テストが、

```text
fatalなんだぜ
successなんだぜ
recoverableなんだぜ
```

の3種類あったとするんだぜ。

でも実装は `recoverable` を特別扱いしてないんだぜ。

coverageだけ見ると、

```text
fatalでif側を通ったんだぜ
successでelse側を通ったんだぜ
もう100%なんだぜ
recoverableのテストは同じelseを通るだけなんだぜ
```

に見えるんだぜ。

だから、

> **recoverableのテストは冗長なんだぜ。**

と消したくなるんだぜ。

でもその「冗長なテスト」こそ、

> **recoverableをsuccess扱いしてるバグ**

を見つけるんだぜ。

GoogleのTesting Blogにも、まさに **coverage上は冗長に見えるテストがバグを露出する** 例が出てるんだぜ。

つまり、

**テストにはcoverageでは見えない冗長性・多様性が必要なんだぜ。**

## 「100%を最小本数で達成」が危ないんだぜ

数学の問題みたいに、

> **最小のテスト数で100% coverageを達成するんだぜ。**

を目標にすると、

```text
同じ行を通るテストを消すんだぜ
似た入力を減らすんだぜ
edge caseを削るんだぜ
```

になりやすいんだぜ。

でもテストで欲しいのは、

> **行を通すこと**

だけじゃないんだぜ。

```text
違う入力なんだぜ
境界値なんだぜ
異常系なんだぜ
壊れ方の違いなんだぜ
過去のバグなんだぜ
組み合わせなんだぜ
```

を試すことなんだぜ。

coverage上は同じ行を通っていても、

**意味の違うテストは全然冗長じゃないんだぜ。**

## assertが何も見てなくてもcoverageは上がるんだぜ

極端な話、

```python
def test_something():
    do_important_work()
```

だけでも、`do_important_work()` の中はcoverageされるんだぜ。

でも、

```text
返り値が正しいんだぜ？
DBが正しく更新されたんだぜ？
エラーが出るべきところで出たんだぜ？
副作用が正しいんだぜ？
```

を何も確認してないかもしれないんだぜ。

coverageが見てるのは、

> **実行したんだぜ。**

なんだぜ。

> **正しさを確認したんだぜ。**

じゃないんだぜ。

だからGoogleも、

> **coverageはcovered lineが正しくtestedされたことを保証せず、test中にexecutedされたことしか保証しない**

と説明してるんだぜ。

## 「存在しない処理」はcoverageでは見つからないんだぜ

もっと怖いのがこれなんだぜ。

必要な処理そのものを書き忘れてる場合なんだぜ。

例えば仕様は、

```text
fatalなら停止なんだぜ
recoverableなら復旧なんだぜ
successなら続行なんだぜ
```

なのに、コードが、

```python
if code == "fatal":
    stop()
else:
    continue_work()
```

しかなかったんだぜ。

このコードの全行を実行すればcoverage 100%にできるんだぜ。

でも、

**recoverable用の処理そのものが存在しない**

んだぜ。

coverageは、

> **書いてあるコードをどれだけ通したんだぜ？**

は測れるんだぜ。

でも、

> **本来あるべきなのに書き忘れたコードはあるんだぜ？**

は測れないんだぜ。

存在しない行はcoverageの分母にも入らないんだぜ。

## 100%をノルマにするとテストが変な方向へ進むんだぜ

例えば組織で、

> **100%未満はmerge禁止なんだぜ。**

にしたんだぜ。

すると人間は100%を達成するんだぜ。

でも必ずしも品質を上げる方向とは限らないんだぜ。

```text
意味の薄いテストを書くんだぜ
とにかく一回呼ぶんだぜ
coverage対象から除外するんだぜ
テストしにくいコードを無理やり通すんだぜ
```

みたいなゲームになり得るんだぜ。

Google Testing Blogも、100%へ近づけること自体に集中すると、

```text
false sense of securityなんだぜ
低価値テストが増えるんだぜ
そのテストの保守コストまで増えるんだぜ
```

という問題を指摘してるんだぜ。

**測定値を目標にすると、測定値を良くするゲームが始まるんだぜ。**

## coverageが低いのは普通に怪しいんだぜ

じゃあcoverageは意味ないんだぜ？

そんなことはないんだぜ。

例えば重要な処理なのに、

```text
coverage 20%なんだぜ
```

なら、

> **そもそも全然テストしてないんじゃないんだぜ？**

という強いシグナルなんだぜ。

coverageは、

> **どこをテストしてないんだぜ？**

を見つけるにはかなり便利なんだぜ。

Googleもcoverageを、

**テストが足りない場所を探す道具**

として使う価値を認めてるんだぜ。

つまり、

> **coverageは地図なんだぜ。**

なんだぜ。

> **品質の点数表なんだぜ。**

ではないんだぜ。

## 100%でもテストケースには冗長性が要るんだぜ

ここで最初の話へ戻るんだぜ。

```text
同じ行を何回も通るんだぜ
```

だけ見ると無駄に見えるんだぜ。

でも、

```text
0なんだぜ
1なんだぜ
最大値なんだぜ
負数なんだぜ
空文字なんだぜ
長い文字列なんだぜ
壊れた入力なんだぜ
過去にバグった入力なんだぜ
```

を通す意味は全然違うんだぜ。

実行するコードが同じでも、

**壊れる条件が同じとは限らないんだぜ。**

だから、

> **coverage 100%だから、もう追加テストは冗長なんだぜ。**

ではないんだぜ。

むしろ100%になったあとから、

> **同じコードに違う角度から何をぶつけるんだぜ？**

が本番なんだぜ。

## だからなんだぜ

コードカバレッジ100%は悪いことじゃないんだぜ。

自然に100%になって、しかもテストがちゃんとしてるなら素晴らしいんだぜ。

でも、

> **100%だから安全なんだぜ。**

は危ないんだぜ。

coverageは、

```text
コードを通ったんだぜ
```

を測るんだぜ。

テスト品質は、

```text
正しい入力を試したんだぜ
異常系を試したんだぜ
境界値を試したんだぜ
期待結果を確認したんだぜ
仕様漏れを見つけるんだぜ
```

まで見るんだぜ。

**100% coverageは、テストの終点じゃないんだぜ。**

**むしろ「同じコードを、別の壊し方でも試せてるんだぜ？」と考えるところからなんだぜ。**
