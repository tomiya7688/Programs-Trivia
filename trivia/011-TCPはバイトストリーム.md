# #011 TCPってな、メッセージを送ってるわけじゃないんだぜ

ネットワークプログラムを書き始めると、こんなコードを書くんだぜ。

```python
sock.send(b"HELLO")
sock.send(b"WORLD")
```

すると気分としては、

```text
HELLO というメッセージを送るんだぜ
WORLD というメッセージを送るんだぜ
```

なんだぜ。

だから受信側でも、

```python
a = sock.recv(1024)
b = sock.recv(1024)
```

とやれば、

```text
a = HELLO
b = WORLD
```

になる気がするんだぜ。

でもな。

**TCPはそんな約束をしてないんだぜ。**

### TCPが運んでるのは「メッセージ」じゃなくてバイト列なんだぜ

TCPの仕様では、TCPはアプリケーションに対して **reliable, in-order, byte-stream service** を提供するんだぜ。

つまり、

```text
順番どおりなんだぜ
途中で消えたら再送するんだぜ
でも区切りは知らないんだぜ
```

なんだぜ。

TCPからすると、

```text
HELLO
WORLD
```

じゃなくて、

```text
HELLOWORLD
```

という **10バイトの流れ** なんだぜ。

どこで `send()` を呼んだかなんて、受信側にそのまま伝える義務はないんだぜ。

### sendを2回してもrecvが2回とは限らないんだぜ

送信側が、

```python
sock.sendall(b"HELLO")
sock.sendall(b"WORLD")
```

としたとしても、受信側では例えば、

```text
recv() → HELLOWORLD
```

と一発で来ることもあるんだぜ。

逆に、

```text
recv() → HE
recv() → LLO
recv() → WOR
recv() → LD
```

みたいに細切れになることもあるんだぜ。

あるいは、

```text
recv() → HELLOW
recv() → ORLD
```

なんて区切りもあり得るんだぜ。

**送ったときの区切りと、受け取るときの区切りには対応関係がないんだぜ。**

RFC 9293にも、アプリケーションのread/write bufferの境界とTCP segmentの境界には相関を保証しない、と明記されてるんだぜ。

### TCPパケットの境界すら、アプリから見たメッセージ境界じゃないんだぜ

ここで、

> **じゃあTCPパケット1個を1メッセージだと思えばいいんだぜ？**

となりそうなんだぜ。

それも違うんだぜ。

TCPは内部ではデータを **segment** に分けてネットワークへ流すんだぜ。

でもsegmentをどう切るかは、

```text
MSSなんだぜ
輻輳制御なんだぜ
送信バッファなんだぜ
Nagleなんだぜ
OSの都合なんだぜ
ネットワークの都合なんだぜ
```

みたいな要因で変わるんだぜ。

アプリケーションが、

```text
ここからここまでが1個のメッセージなんだぜ
```

と思っていても、TCP自身は知らないんだぜ。

**TCP segmentはアプリケーションのメッセージじゃないんだぜ。**

### じゃあメッセージの区切りは誰が決めるんだぜ

**アプリケーション側なんだぜ。**

例えばHTTP/1.xなら、

```text
Content-Length: 123
```

みたいに長さを書くんだぜ。

あるいは改行で区切るプロトコルなら、

```text
HELLO\n
WORLD\n
```

みたいにするんだぜ。

他にも、

```text
最初の4バイトに長さを書くんだぜ
そのあとに本体を書くんだぜ
```

みたいな **length prefix** を使うんだぜ。

例えば、

```text
[0005][HELLO][0005][WORLD]
```

みたいな感じなんだぜ。

つまりTCPの上でメッセージ通信をしたいなら、

> **どこまでが1メッセージなのかを、自分たちで決めるんだぜ。**

なんだぜ。

### だからrecv(1024)は「1024バイト受け取る」じゃないんだぜ

これも初心者がハマるところなんだぜ。

```python
data = sock.recv(1024)
```

を見ると、

> **1024バイト受信するんだぜ。**

に見えるんだぜ。

でも普通は、

> **最大1024バイトまで受け取るんだぜ。**

なんだぜ。

今受信バッファに30バイトしか来てなければ、30バイトで返ることがあるんだぜ。

だから、

```python
header = sock.recv(100)
```

として、

> **100バイトのヘッダが取れたんだぜ。**

と思ったら事故るんだぜ。

必要なバイト数が決まっているなら、足りるまで繰り返して読む必要があるんだぜ。

### 送る側も一発で全部送れるとは限らないんだぜ

低レベルな `send()` は、

```text
渡したデータを全部送ったんだぜ
```

とは限らないんだぜ。

一部だけ送って、

```text
ここまでは受け取ったんだぜ
残りはまた呼んでくれなんだぜ
```

になることがあるんだぜ。

だからPythonには `sendall()` があるし、他の言語やAPIでも「全部書けるまでループする」処理が必要になることがあるんだぜ。

ここでもTCPは、

**メッセージ単位じゃなくて、バイトの流れなんだぜ。**

が効いてくるんだぜ。

### UDPはこの点では話が違うんだぜ

UDPは **datagram** を送るんだぜ。

つまり送信側が1個のdatagramとして送ったものは、受信側でも1個のdatagramとして扱われるんだぜ。

TCPみたいに、

```text
HELLO + WORLD
```

が勝手に、

```text
HELLOWORLD
```

という一続きのストリームになるわけじゃないんだぜ。

もちろんUDPには、

```text
届かないかもしれないんだぜ
順番が変わるかもしれないんだぜ
重複するかもしれないんだぜ
```

という別の問題があるんだぜ。

だから、

```text
TCP = 信頼できるバイトストリームなんだぜ
UDP = メッセージ境界を持つdatagramなんだぜ
```

くらいに見ると違いが分かりやすいんだぜ。

### だからなんだぜ

TCPで、

```text
send("HELLO")
send("WORLD")
```

したんだぜ。

人間は、

> **2個のメッセージを送ったんだぜ。**

と思うんだぜ。

TCPは、

> **10バイト預かったんだぜ。順番どおり届けるんだぜ。区切り？ 知らないんだぜ。**

なんだぜ。

ここを知らないと、

```text
たまにJSONが途中で切れるんだぜ
たまに2個のJSONがくっつくんだぜ
ローカルでは動くのに本番で壊れるんだぜ
```

みたいなネットワークバグになるんだぜ。

**TCPはメッセージ配送サービスじゃないんだぜ。**

**順番のある、信頼できるバイトの川なんだぜ。**
