# #035 Use-After-Freeってな、解放したメモリをまた使うことなんだぜ！

セキュリティニュースを読んでいると、やたら出てくる言葉があるんだぜ。

**Use-After-Free（ユーズ・アフター・フリー、略してUAF）**。

「またこの脆弱性が出たんだぜ！ CVSSが高いんだぜ！」

……と言われても、

**「おいおい、そもそも何をどうしたら危ないんだぜ？」**

と思う人も多いはずなんだぜ。

実は名前の意味はそのまま、**「解放したメモリを、あとから使ってしまう」** ということなんだぜ。

## まずホテルの部屋で考えるんだぜ！

ホテルの部屋を借りるんだぜ。

~~~text
① チェックインするんだぜ
   → 301号室が使えるんだぜ！

② チェックアウトするんだぜ
   → 301号室をホテルに返したんだぜ！

③ 古いカードキーを持っているんだぜ
   → でも、もう301号室を使う権利はないんだぜ！

④ 古いカードキーでまた入ろうとするんだぜ
   → おいおい、次の客が使ってるかもしれないんだぜ！
~~~

この④が **Use-After-Freeのイメージ**なんだぜ！

メモリも同じで、プログラムは必要な領域を確保して、使い終わったら解放するんだぜ。

でも、**解放する前のアドレスを覚えているポインタが残っていると、間違ってその領域を読んだり書いたりする**ことがあるんだぜ。

ちなみに、**解放したからといって、そのメモリの中身が自動で全部ゼロになるとは限らない**んだぜ。「古いデータが見えたから使っていい」は大間違いなんだぜ。

## メモリの中では何が起きるんだぜ？

例えば、プログラムがメモリのある場所を確保したとするんだぜ。

~~~text
確保したんだぜ
  p ─────→ [ 42 ]   ← メモリの領域A

使い終わって解放するんだぜ
  p ─────→ [ 解放済み ]   ← Aを使う権利はもうないんだぜ

別の処理がその場所を再利用することもあるんだぜ
  q ─────→ [ 別のデータ ] ← 領域A

それなのに古いpで読み書きするんだぜ
  p ─────→ [ 別のデータ ] ← UAFなんだぜ！
~~~

※解放した領域が**必ず同じアドレスで再利用されるわけではない**んだぜ。ここは起こり得る例を描いているんだぜ。

ポイントは、**ポインタがアドレスを覚えていることと、そのメモリを使っていいことは別**だということなんだぜ。

解放後に使い物にならなくなった参照は、**ダングリングポインタ（dangling pointer）** と呼ばれるんだぜ。

## C言語の短い例を見るんだぜ

こんなコードを考えるんだぜ。

```c
#include <stdlib.h>

int main(void) {
    int *p = malloc(sizeof *p);
    if (p == NULL) return 1;

    *p = 42;             // 確保したメモリを使うんだぜ
    int *alias = p;      // 同じ場所を別の名前でも覚えるんだぜ

    free(p);             // その場所を返したんだぜ！
    p = NULL;            // pをNULLにするのはいいんだぜ

    // *alias = 99;      // ← これを実行したらUAFなんだぜ！
    // aliasは自動ではNULLにならないんだぜ

    return 0;
}
```

**`free(p)` はメモリの利用を終わらせる操作**なんだぜ。

ところが、`alias` も同じ領域を指していたんだぜ。`p = NULL` としても、**別のポインタまで勝手に書き換わるわけじゃない**んだぜ。

コメントアウトした行を有効にすると、もう使ってはいけない領域へ書き込もうとすることになるんだぜ。

CやC++ではこうしたアクセスは **未定義動作（undefined behavior）** なんだぜ。

「いつもクラッシュする」「いつも99が書ける」のどちらも保証されないんだぜ。

**たまたま動いて見えるのが、むしろ厄介なんだぜ！**

## なんで重大な脆弱性になるんだぜ？

解放済みのメモリを触ると、状況によってはこんなことが起きるんだぜ。

- **クラッシュ**：プログラムが落ちたり、サービスが停止したりするんだぜ。
- **データ破壊や情報漏えい**：別の処理が使っているデータを壊したり、本来見えない値を読んだりすることがあるんだぜ。
- **任意コード実行**：攻撃者がメモリの再利用や処理の流れを都合よく操れる場合、コード実行につながることもあるんだぜ。

でも、**UAFがあるだけで、絶対に遠隔からrootを取れるわけじゃない**んだぜ。

危険度は、その領域にどんなデータが入り、誰がどんな入力を送れて、どこで処理されるかによるんだぜ。

MITREではUAFを **CWE-416** として分類しているんだぜ。

## 自分でfreeしてないのに起きることもあるんだぜ！

例えばCPUやスレッドが複数ある場合なんだぜ。

~~~text
スレッドA：あるデータを読んでるんだぜ
         ↓
スレッドB：もう不要だと思って解放したんだぜ
         ↓
スレッドA：まだ読んでるんだぜ！
         ↓
おいおい、解放済みメモリだったんだぜ！
~~~

これは、処理のタイミングがぶつかる **競合状態（race condition）** が原因の一例なんだぜ。

Linuxカーネルの[CVSS 9.8のTCP脆弱性ニュース](../news/2026/10/tech/2026-10-31-LinuxカーネルのTCP脆弱性.md)でも、こうした競合に関係するUAFを紹介したんだぜ。

ただし、**UAFが全部マルチスレッド由来というわけじゃない**んだぜ。単純な解放後アクセスや、所有者・寿命の管理ミスでも起きるんだぜ。

## Double-Freeとは違うんだぜ！

似た名前のバグと並べると分かりやすいんだぜ。

| 名前 | 何を間違えたんだぜ？ |
| --- | --- |
| **Use-After-Free（UAF）** | 解放したあとに**使う**んだぜ |
| **Double-Free** | 同じメモリを**2回解放**しようとするんだぜ |
| **メモリリーク** | もう使わないメモリを**解放し忘れる**んだぜ |
| **バッファオーバーフロー** | 確保した領域の**範囲外へアクセス**するんだぜ |

全部メモリの扱い方の問題だけど、同じバグじゃないんだぜ！

## どうすれば防げるんだぜ？

基本は、**誰がメモリを所有しているのか、いつまで使えるのかを間違えない**ことなんだぜ。

C++ならRAIIや`std::unique_ptr`などを活用し、解放の責任を明確にする方法があるぜ。必要なら共有所有権の扱いにも注意するんだぜ。

Rustなら、所有権と借用の仕組みによって**通常の安全なコードでは解放済みの参照を使えないようにする**設計なんだぜ。ただし`unsafe`や外部ライブラリとの境界まで無条件に安全になるわけじゃないんだぜ。[Rustのメモリ安全の話](003-Rustは完全なメモリ安全ではない.md)も読んでみるんだぜ。

C/C++の検査では、Clangなどの **AddressSanitizer（ASan）** がUAFを見つける助けになるんだぜ。

例えば、**開発用のテストビルド**で`-fsanitize=address`を使うんだぜ。

ただし、テストで見つからなかったからといって、**UAFが絶対ないという保証にはならない**んだぜ。静的解析、ファジング、レビューなどと組み合わせるんだぜ。

## だからなんだぜ

**Use-After-Freeは、「解放したメモリを使う」という、名前どおりのバグなんだぜ！**

分かってしまえば単純なんだぜ。

でも、古いポインタ、複数スレッド、複雑な所有権が絡むと、見つけるのも防ぐのも難しくなるんだぜ。

**「もう返したんだぜ！」→「でもまだ使ってるんだぜ！」**

……**おいおい、そりゃ大変なんだぜ！**

次にセキュリティニュースでUAFという言葉を見たら、**「もう使っちゃいけないメモリに触ってるんだぜ」**と思い出すといいんだぜ！
