# Programs-Trivia

プログラムの「実はこうなんだぜ」を集めるリポジトリなんだぜ。

コードそのものを書くというより、言語の仕様、歴史、変な挙動、よくある誤解なんかを「実はこうなんだぜ」のノリで眺めていくんだぜ。

---

## #001 クラスはオブジェクト指向より前なんだぜ

今だと、

**クラス → オブジェクト → オブジェクト指向**

みたいな順番で習うことが多いんだぜ。

だから「オブジェクト指向という考え方が先にあって、そのためにクラスが作られた」と思いがちなんだぜ。

でも歴史はそんなに素直じゃないんだぜ。

### 1965年にはもう `record class` がいたんだぜ

1965年、C. A. R. Hoare は ALGOL の拡張案として **Record Handling** を発表しているんだぜ。

そこではすでに、

```
record class
```

という言葉が使われていて、レコードをクラスに所属させたり、サブクラスを扱ったりする考え方まで出てくるんだぜ。

つまり、現在のクラスにつながる系譜は「オブジェクト指向」という名前が確立するより前から育っていたんだぜ。

### それを Simula が拾ったんだぜ

その後、Ole-Johan Dahl と Kristen Nygaard が Simula 67 を作る過程で、Hoare の record class / subclass の考え方を取り込みながら、**class と、その class に属する object** という形へ発展させていったんだぜ。

Simula 67 ではクラスが単なるデータの型ではなく、処理も持てるようになって、継承につながる仕組みも入ってきたんだぜ。

ここまで来ると、かなり今の「クラス」の顔になってくるんだぜ。

### 「オブジェクト指向」という名前は後から来たんだぜ

Alan Kay と Smalltalk の流れで **object-oriented programming** という言葉が生まれ、オブジェクトを中心にプログラムを考える思想がはっきり名前を持つようになったんだぜ。

だから、

> **オブジェクト指向が完成して、その部品としてクラスが発明されたわけじゃないんだぜ。**
>
> **クラスやオブジェクトにつながる仕組みが先に育って、その流れが後から「オブジェクト指向」という名前を持ったんだぜ。**

という見方ができるんだぜ。

### ただし厳密には、なんだぜ

Simula 67 は一般に「最初のオブジェクト指向言語」とされているんだぜ。

だから「クラスはオブジェクト指向より前なんだぜ」というのは、

**クラスの系譜や用語が、オブジェクト指向という名前・確立したパラダイムより先に現れていたんだぜ**

という意味なんだぜ。

こういう「教科書で見る順番と、歴史上できた順番は違うんだぜ」が今回の雑学なんだぜ。

## #002 Pythonはインタプリタ言語……だけじゃないんだぜ

Pythonって「インタプリタ言語」だって習うことが多いんだぜ。

たしかに、普段の使い方を見るとそう見えるんだぜ。

```bash
python hello.py
```

コンパイル用のコマンドを叩かなくても、そのまま実行できるんだぜ。

でも、少なくとも一番よく使われている実装の **CPython** は、Pythonのソースコードをそのまま1行ずつ読んで実行しているわけじゃないんだぜ。

### 実は一回コンパイルしてるんだぜ

CPythonはPythonのソースコードを、まず **バイトコード** にコンパイルするんだぜ。

そして、そのバイトコードをCPythonのインタプリタが実行するんだぜ。

ざっくり書くと、

```text
Pythonのソースコード
        ↓
     コンパイル
        ↓
   CPythonのバイトコード
        ↓
     インタプリタ
        ↓
       実行
```

なんだぜ。

だから、

> **Pythonはインタプリタで実行されるんだぜ**

は間違いじゃないんだぜ。

でも、

> **Pythonはコンパイルされないんだぜ**

は違うんだぜ。

### バイトコードは自分でも見られるんだぜ

Pythonには `dis` という標準モジュールがあるんだぜ。

例えば、

```python
def add(a, b):
    return a + b
```

を逆アセンブルすると、CPythonが実際に扱うバイトコード命令を見ることができるんだぜ。

```python
import dis

dis.dis(add)
```

つまり「裏ではコンパイルしてるんだぜ」は比喩じゃなくて、本当に確認できるんだぜ。

### そもそもインタプリタとコンパイラは別次元の話なんだぜ

ここで一回、言葉を整理するんだぜ。

**コンパイラ**は、ざっくり言えば **あるプログラム表現を別のプログラム表現へ変換する機械** なんだぜ。

ソースコードを機械語に変えることもあるし、ソースコードをバイトコードに変えることもあるんだぜ。

つまり仕事は **変換** なんだぜ。

一方で **インタプリタ** は、ざっくり言えば **命令を読んで、その意味どおりに実行する機械** なんだぜ。

言ってしまえば、命令を受け取って動く「コマンドマシン」みたいなものなんだぜ。

つまり仕事は **実行** なんだぜ。

だから、

> **コンパイラか、インタプリタか**

という二択に見えるけど、本当は役割が違うんだぜ。

コンパイラは「変換するやつ」で、インタプリタは「実行するやつ」なんだぜ。

なので、

```text
ソースコード
    ↓ コンパイラ
バイトコード
    ↓ インタプリタ
実行
```

みたいに、**同じ処理系の中に両方いても全然おかしくない**んだぜ。

むしろCPythonがまさにそれなんだぜ。

ただし厳密には、コンパイラの入力も出力も必ず「テキスト」とは限らないんだぜ。

ASTや中間表現、バイトコード、機械語みたいな形を相手にすることもあるんだぜ。

だから一番雑味の少ない言い方をすると、

> **コンパイラはプログラムを別の表現に変換するんだぜ。**
>
> **インタプリタはプログラムや命令列を実行するんだぜ。**

なんだぜ。

### 面白いことに、CPUもインタプリタみたいなもんなんだぜ

ここまで来ると、ちょっと見方が変わるんだぜ。

CPUも、機械語の命令を読んで、

```text
この命令なら足し算するんだぜ
この命令ならメモリから読むんだぜ
この命令ならジャンプするんだぜ
```

みたいに、その命令の意味どおりに状態を変えていくんだぜ。

だからかなり雑に言えば、

> **CPUは機械語を実行する、ハードウェア製のインタプリタみたいなもんなんだぜ。**

とも見られるんだぜ。

もちろん実際のCPUの中身はもっと複雑なんだぜ。

命令を分解したり、先読みしたり、並列に実行したり、場合によってはマイクロコードを使ったりするんだぜ。

だから「CPUそのものがインタプリタなんだぜ」と厳密に定義するというより、

**命令列を読み、その意味に従って実行するという役割はインタプリタとよく似てるんだぜ**

くらいに捉えると面白いんだぜ。

そう考えると、

```text
Pythonソース
    ↓ コンパイラ
Pythonバイトコード
    ↓ CPythonのインタプリタ
機械語として動くCPython
    ↓ CPU
実行
```

みたいに、下へ降りても「命令を読んで実行するやつ」がまた出てくるんだぜ。

### しかも「Python＝インタプリタ方式」でもないんだぜ

ここがさらに面白いところなんだぜ。

**Pythonは言語で、CPythonはその実装のひとつ**なんだぜ。

Pythonという言語そのものが、

「必ずこの方法で実行しろ」

と決めているわけじゃないんだぜ。

例えば **PyPy** にはJITコンパイラがあって、実行中にコードをマシンコードへコンパイルして高速化するんだぜ。

だから、

**コンパイル言語か、インタプリタ言語か**

という二択は、思っているほど綺麗に分かれないんだぜ。

むしろ、

**その言語を、どんな処理系が、どう実行しているか**

の話なんだぜ。

### つまりなんだぜ

Pythonを最初に習うときは、

> Pythonはインタプリタ言語なんだぜ

で十分なんだぜ。

でも一段奥に行くと、

> **CPythonはソースコードをバイトコードへコンパイルして、そのバイトコードをインタプリタで実行してるんだぜ。**

になるんだぜ。

さらに一段奥に行くと、

> **そもそも「コンパイル言語」と「インタプリタ言語」は、言語そのものを完全に二分する分類じゃないんだぜ。**

になるんだぜ。

教科書の分類を一枚めくると、急に世界が曖昧になるんだぜ。

## #003 Rustってな、実は完全なメモリ安全じゃないんだぜ

Rustといえば **メモリ安全** なんだぜ。

所有権、借用、ライフタイム、境界チェックなんかで、CやC++でありがちなメモリ破壊をかなりのところまで防いでくれるんだぜ。

特に **Safe Rustだけを書いている限り、メモリ安全なんだぜ** と説明されることが多いんだぜ。

でもな。

現実に動くプログラムは、Rustの型システムだけで出来ているわけじゃないんだぜ。

```text
Rustのコード
    ↓
rustc
    ↓
LLVM
    ↓
機械語
    ↓
CPU
```

なんだぜ。

つまり、Rust側でどれだけ安全性を証明しても、**その下でコンパイラが間違った機械語を作ったら終わりなんだぜ。**

### Safe Rustなのにsegfaultしたことがあるんだぜ

2020年のRust 1.41.0では、実際に **Safe RustのコードがLLVMのmiscompileによってsegfaultする** バグが報告されたんだぜ。

Issueのタイトルもそのまんま、

> **Memory unsafety problem in safe Rust**

なんだぜ。

問題のプログラムでは、範囲外のsliceアクセスをしようとしていたんだぜ。

普通ならRustの境界チェックが働いて、

```text
index out of bounds
```

でpanicするはずなんだぜ。

つまりプログラムとしては間違っていても、**メモリの外を勝手に読む前にRustが止める**はずなんだぜ。

ところが最適化を有効にしたRust 1.41.0では、sliceの長さがおかしな値になり、境界チェックまで消えて、最後はsegmentation faultしたんだぜ。

Safe Rustなのにだぜ。

### 犯人はLLVMの最適化だったんだぜ

調査すると、Rustの型チェックやborrow checkerが間違っていたわけじゃなかったんだぜ。

Miriでは問題なく、最適化前の段階でも筋は通っていたんだぜ。

壊れたのは、その後なんだぜ。

LLVM 9の **Scalar Evolution / Induction Variable Simplification** 周辺の最適化で、本当は保証できない計算に対して

```text
nuw
```

つまり **「unsigned overflowしないんだぜ」** という印を付けてしまうバグがあったんだぜ。

LLVMはその印を信じて、

「じゃあこの条件はこうなるはずなんだぜ」

と最適化を進めた結果、本来必要だった境界チェックまで消してしまったんだぜ。

**コンパイラは、嘘の前提を1個信じるだけで安全装置まで消せるんだぜ。**

### しかもLLVM側ではもう直ってたんだぜ

このLLVMの変更はLLVM 9に入っていたんだぜ。

でも問題が見つかって、LLVM本家では後にその変更がrevertされていたんだぜ。

LLVM 10では修正済みだったんだぜ。

ところがRust 1.41.0はLLVM 9系のsnapshotを使っていたので、そのバグを踏んだんだぜ。

RustチームはRust 1.41.1でLLVM側のrevertをcherry-pickして修正したんだぜ。

Rust公式の1.41.1リリース記事にも、

**LLVMの最適化によって境界チェックが誤って消え、segfaultしていた**

とちゃんと書かれているんだぜ。

### じゃあRustはメモリ安全じゃないのか、なんだぜ

ここが大事なんだぜ。

Rustの **言語としてのSafe Rustのルール** は、メモリ安全になるように設計されているんだぜ。

でもその保証を現実の機械まで持っていくには、

```text
型システムが正しい
rustcが正しい
LLVMが正しい
標準ライブラリのunsafe実装が正しい
CPUが正しく動く
```

みたいな前提が必要なんだぜ。

だから、

> **Safe Rustなら、どんなコンパイラバグがあっても絶対にメモリ事故は起こらないんだぜ**

ではないんだぜ。

より正確には、

> **Safe Rustは、正しい処理系の上ではメモリ安全になるように設計されているんだぜ。**

なんだぜ。

この話の面白いところは、

**安全な言語でも、最後には安全じゃないくらい巨大な下の層を信用してるんだぜ**

ってところなんだぜ。

## #004 実はAIってな、厳密な定義はないんだぜ

今じゃ何でもかんでも **AI** って呼ばれてるんだぜ。

生成AI、画像認識、音声認識、自動運転、レコメンド、ゲームAI。

でもな。

**そもそも「どこからどこまでがAIなのか」には、世界共通の一本きりの厳密な定義がないんだぜ。**

OECDですら、

> **AIには普遍的に受け入れられた定義はないんだぜ**

という前提から話を始めてるんだぜ。

NISTの用語集を見ても、AIには複数の定義が並んでるんだぜ。

つまり「AI」という言葉は、数学の定理みたいに境界線が一本引かれている言葉じゃないんだぜ。

### 言葉どおりに受け取ると、電卓だってAIなんだぜ

AIは **Artificial Intelligence** なんだぜ。

直訳すれば **人工知能** なんだぜ。

じゃあ「知能」って何なんだぜ。

計算する能力は知能じゃないのか、なんだぜ。

人間が暗算すれば知的活動っぽいのに、

```text
123456 × 789012
```

を電卓が一瞬で解いたら、急に「ただの計算機」になるんだぜ。

でも電卓は、人間が頭を使ってやっていた計算を人工物で代行してるんだぜ。

だから **Artificial Intelligenceという言葉をものすごく素朴に読むなら、電卓までAIに入れてもおかしくなくなってくるんだぜ。**

もちろん、今の普通の使い方では電卓をAIとは呼ばないんだぜ。

ここがポイントなんだぜ。

### じゃあなんで電卓はAIじゃないんだぜ

現代のAIの定義では、

- 入力から何かを推論するんだぜ
- 予測や判断をするんだぜ
- 人間っぽい認知的な仕事をするんだぜ
- 学習したり、ある程度自律的に振る舞ったりするんだぜ

みたいな条件を置くことが多いんだぜ。

そうすると、決められた算術規則をそのまま実行する普通の電卓はだいたい外れるんだぜ。

でも、その条件の置き方自体がひとつじゃないんだぜ。

**AIかどうかを決めるには、先に「知能とは何なんだぜ」を決めないといけないんだぜ。**

そして、そこがもう難問なんだぜ。

### しかも「AIらしさ」はブームごとに変わってきたんだぜ

AIの歴史を見ると、この曖昧さがもっと分かりやすいんだぜ。

1956年のダートマス会議で **Artificial Intelligence** という名前が研究分野として打ち出されたんだぜ。

ここから始まる第1次AIブームでは、主役は **探索と推論** だったんだぜ。

```text
迷路を解くんだぜ
定理を証明するんだぜ
チェスを指すんだぜ
```

みたいなことが、

> **機械が考えてるんだぜ**

と感じられた時代なんだぜ。

今見ると、探索アルゴリズムやルールベースのプログラムに見えるものでも、当時はAI研究のど真ん中だったんだぜ。

でも現実世界は探索する組み合わせが多すぎて、簡単な問題では強くても複雑な現実問題にはなかなか勝てなかったんだぜ。

そして期待がしぼんで、いわゆる **冬の時代** に入るんだぜ。

### 第2次AIブームでは「知識を持ってるやつ」がAIだったんだぜ

1980年代に来た第2次AIブームでは、主役が **エキスパートシステム** になったんだぜ。

専門家が持っている知識を大量のルールとしてコンピュータに入れて、

```text
もしAでBならCなんだぜ
もし症状XとYなら病気Zを疑うんだぜ
```

みたいに推論させるんだぜ。

つまりこの時代のAIは、

> **ものをたくさん知っていて、専門家みたいに判断する機械なんだぜ**

というイメージだったんだぜ。

ところが、人間の知識を全部ルールとして書き出して保守するのは大変すぎたんだぜ。

知識を増やせば増やすほど管理も重くなって、また期待がしぼんでいったんだぜ。

### 第3次AIブームでは「自分で学ぶやつ」がAIになったんだぜ

2000年代以降、特に2010年代になると、主役は **機械学習とディープラーニング** になったんだぜ。

今度は人間がルールを全部書くんじゃなくて、

```text
データを渡すんだぜ
        ↓
パターンを学ばせるんだぜ
        ↓
予測や分類をさせるんだぜ
```

という方向になったんだぜ。

経産省の資料でも、

```text
第1次AIブーム → 探索・推論
第2次AIブーム → 知識
第3次AIブーム → 機械学習・ディープラーニング
```

という整理がされているんだぜ。

つまり面白いことに、

> **その時代に「機械がこんなことまで出来るのか」と驚かれる能力が、AIの顔になってきたんだぜ。**

なんだぜ。

### 昔AIだったものが、普通の機能になることもあるんだぜ

さらに面白いのが **AI effect** なんだぜ。

昔は、

「こんなのコンピュータにできたら知能なんだぜ」

と思われていた仕事でも、できるのが当たり前になると、

「いや、それはただのアルゴリズムなんだぜ」

みたいにAI扱いされなくなることがあるんだぜ。

チェス、文字認識、音声認識なんかも、時代によって「AIっぽさ」の感じ方が変わってきたんだぜ。

つまりAIという言葉の境界線は、技術が進むと一緒に動くんだぜ。

### だから「AIを使ってる」は思ったより曖昧なんだぜ

「この製品はAIを使っています」

と言われても、それだけでは技術的な説明としてはかなり弱いんだぜ。

機械学習なのか。

ニューラルネットワークなのか。

ルールベースなのか。

統計モデルなのか。

大規模言語モデルなのか。

それとも単に「賢そうに見える処理」をAIと呼んでいるのか。

**AIという名前だけでは、中身はほとんど分からないんだぜ。**

だから、

> **AIって何なんだぜ？**

と聞かれたとき、本当に正確な最初の答えは、

> **まず、ここでいうAIをどう定義するか決めるんだぜ。**

なのかもしれないんだぜ。

そして言葉を限界まで素朴に受け取れば、

> **電卓だってAIなんだぜ。**

というところまで行けてしまうんだぜ。

もちろん普段はそう呼ばないんだぜ。

**その「普段は呼ばない」が、AIという言葉の境界が社会的・歴史的にも決まっている証拠なんだぜ。**

## #005 プログラムの説明に出てくる数式ってな、数学に戻すとすげーしょうもないことが多いんだぜ

プログラミングとかAIの説明を読んでると、急に数式が出てくるんだぜ。

```text
f(x)
Σ
e^x
max(0, x)
```

このへんが並び始めると、

> **なんか急に高度な数学が始まったんだぜ**

って気分になるんだぜ。

でもな。

**記号を日本語に戻してみると、やってること自体はびっくりするくらい単純だったりするんだぜ。**

### ReLUなんて「マイナスなら0、それ以外はそのまま」なんだぜ

ニューラルネットワークでよく出てくる **ReLU関数** は、

```text
ReLU(x) = max(0, x)
```

なんだぜ。

数式で書くとそれっぽいんだぜ。

でも日本語にすると、

```text
xがマイナスなら0なんだぜ
それ以外ならxをそのまま返すんだぜ
```

なんだぜ。

コードにすると、

```python
def relu(x):
    return max(0, x)
```

なんだぜ。

もっと露骨に書けば、

```python
def relu(x):
    if x < 0:
        return 0
    return x
```

なんだぜ。

急にしょうもなく見えてくるんだぜ。

### シグマも「全部足すんだぜ」なんだぜ

数学でよく出てくる、

```text
Σ
```

も見た目は強そうなんだぜ。

でもだいたい意味は、

> **決められた範囲を全部足すんだぜ**

なんだぜ。

例えば、

```text
Σ xᵢ
```

なら、プログラムではかなり雑に、

```python
total = 0

for x in values:
    total += x
```

なんだぜ。

つまり **for文で足してるだけなんだぜ。**

### 平均二乗誤差も名前ほど怖くないんだぜ

機械学習でよく見る **平均二乗誤差、MSE** は、

```text
MSE = (1/n) Σ (y - ŷ)²
```

みたいに書くんだぜ。

でも日本語にすると、

```text
正解と予測の差を出すんだぜ
↓
二乗するんだぜ
↓
全部足すんだぜ
↓
個数で割るんだぜ
```

なんだぜ。

やってることはかなり素朴なんだぜ。

### 内積も「掛けて足すんだぜ」なんだぜ

ベクトルの内積、

```text
a · b
```

もAIやグラフィックスでは大量に出てくるんだぜ。

でも中身は、

```text
a₁b₁ + a₂b₂ + a₃b₃ + ...
```

なんだぜ。

つまり、

> **同じ場所の数字を掛けて、最後に全部足すんだぜ。**

なんだぜ。

これもコードにするとループなんだぜ。

### 数式が難しいんじゃなくて、圧縮率が高いんだぜ

ここが大事なんだぜ。

数式がしょうもないと言っても、数学が無意味って話じゃないんだぜ。

むしろ逆なんだぜ。

例えば、

```text
MSE = (1/n) Σ (yᵢ - ŷᵢ)²
```

だけで、

```text
全データについて
正解と予測値の差を取って
それを二乗して
全部合計して
データ数で割るんだぜ
```

を一行で書けるんだぜ。

**数式は難しいことを書くためのものというより、処理をものすごい密度で圧縮して書く記法なんだぜ。**

だから慣れてないと、

> **難しいことをやってるんだぜ**

に見えるんだけど、

一個ずつ展開すると、

> **足すんだぜ**
>
> **掛けるんだぜ**
>
> **大きい方を取るんだぜ**

だったりするんだぜ。

### もちろん本当に難しい数式もあるんだぜ

ここは言っておくんだぜ。

世の中の数式が全部簡単なわけじゃないんだぜ。

証明も理論も、本当に難しいものはいくらでもあるんだぜ。

でもプログラムや機械学習の入門説明で出てくる数式のかなりの部分は、

**記号の読み方が分からないせいで、実際の処理以上に難しく見えてる**

ことがあるんだぜ。

だから数式を見てビビったら、

> **これコードにすると何行なんだぜ？**

って考えるといいんだぜ。

ReLUなんて、

```python
max(0, x)
```

で終わりなんだぜ。

**数式の威圧感と、処理の難しさは別物なんだぜ。**

> **変わった言語を作ってみたんだぜ**

> **教育や実用のために何年も設計・保守されている処理系なんだぜ**

という世界なんだぜ。

ここが結構おもしろいんだぜ。


みたいなのが「プログラムっぽい」と感じるんだぜ。

みたいな形が自然なんだぜ。

## #007 モニターの発色ってな、実は絵の具と違うんだぜ

色を混ぜるって聞くと、

> **赤と青を混ぜたら紫なんだぜ**

みたいな、絵の具の感覚を思い浮かべることが多いんだぜ。

でもな。

**モニターの色の作り方は、絵の具とは仕組みが逆なんだぜ。**

### モニターは「光を足す」んだぜ

モニターは自分で光を出してるんだぜ。

基本になるのは、

```text
Red
Green
Blue
```

つまり **RGB** なんだぜ。

この3色の光を足していくんだぜ。

だから、

```text
赤 + 緑 = 黄
緑 + 青 = シアン
青 + 赤 = マゼンタ
赤 + 緑 + 青 = 白
```

になるんだぜ。

これを **加法混色** って呼ぶんだぜ。

つまりモニターでは、

> **光を足せば足すほど明るくなるんだぜ。**

なんだぜ。

全部消したら黒なんだぜ。

全部出したら白なんだぜ。

### 絵の具は「光を引く」んだぜ

一方、絵の具は自分で光ってないんだぜ。

外から来た光の一部を吸収して、残った光を反射してるんだぜ。

だから絵の具を混ぜるっていうのは、

> **反射できる光をどんどん減らしていくんだぜ。**

に近いんだぜ。

印刷ではよく、

```text
Cyan
Magenta
Yellow
```

つまり **CMY** を使うんだぜ。

実際の印刷では黒をきれいに出すために **K** を足して、CMYKになるんだぜ。

これは **減法混色** なんだぜ。

つまり絵の具やインクでは、

> **混ぜれば混ぜるほど暗くなるんだぜ。**

なんだぜ。

### 白と黒の作り方が真逆なんだぜ

ここが一番わかりやすいんだぜ。

モニターでは、

```text
光なし = 黒
RGB全部オン = 白
```

なんだぜ。

でも紙とインクでは、

```text
インクなし = 紙の白
インクを重ねる = 黒に近づく
```

なんだぜ。

つまり、

> **モニターの白は「全部出してる」んだぜ。**
>
> **紙の白は「何も塗ってない」んだぜ。**

なんだぜ。

同じ「白」でも作り方が正反対なんだぜ。

### だから画面の色と印刷の色は一致しないんだぜ

モニターで見た鮮やかな色が、

> **印刷したらなんかくすんだんだぜ**

ってことがあるんだぜ。

これは故障じゃないんだぜ。

モニターはRGBの光で作れる色を出していて、印刷はインクと紙の反射で色を作ってるんだぜ。

そもそも **作れる色の範囲が違う** んだぜ。

この「その装置で表現できる色の範囲」を **色域、gamut** って呼ぶんだぜ。

だから、

```text
画面では出せるんだぜ
でも印刷では出せないんだぜ
```

みたいな色も普通にあるんだぜ。

### 「三原色」って一個じゃないんだぜ

学校で「色の三原色」って習うと、

> **三原色って決まった3色があるんだぜ**

と思いがちなんだぜ。

でも実際には、

```text
光の三原色 → RGB
色材の三原色 → CMY
```

みたいに、何を混ぜるかで話が変わるんだぜ。

つまり、

> **赤・青・黄を混ぜる話と、RGBモニターの話を同じルールで考えると混乱するんだぜ。**

なんだぜ。

### だからなんだぜ

モニターの色は、

> **小さい色付きの光を塗ってるんだぜ**

じゃないんだぜ。

正しくは、

> **赤・緑・青の光を足し合わせて、目に色として感じさせてるんだぜ。**

なんだぜ。

絵の具は、

> **光を足してるんじゃなくて、反射する光を削ってるんだぜ。**

なんだぜ。

同じ「色を混ぜる」でも、

**モニターと絵の具では、物理的にはほぼ逆のことをやってるんだぜ。**

## #008 小型コンピュータが安くなかった時代の周辺機器ってな、こんな仕組みだったんだぜ

今の周辺機器って、実は中に小さいコンピュータが入ってることが多いんだぜ。

キーボードにもいるんだぜ。

マウスにもいるんだぜ。

SSDにもいるんだぜ。

プリンタにもいるんだぜ。

モニターにもいるんだぜ。

今なら、

```text
センサーやスイッチを読むんだぜ
        ↓
マイコンで判断するんだぜ
        ↓
モーターや通信を制御するんだぜ
```

みたいに作れるんだぜ。

でもな。

**安いマイクロプロセッサを周辺機器の中にポンと入れられなかった時代は、今ならプログラムで書くような処理を、専用回路や機械仕掛けそのものでやってたんだぜ。**

### キーボードの文字コードを「回路そのもの」が作ってたんだぜ

1969年の **Datapoint 3300** という端末の整備マニュアルを見ると、キーボードの中身がかなり面白いんだぜ。

キーには磁気式のリードスイッチがあるんだぜ。

押すと信号が出るんだぜ。

その信号を **ダイオードマトリクス** に通して、どの文字が押されたかを7本のビット線に変換するんだぜ。

さらに、

```text
キーを押すんだぜ
    ↓
リードスイッチが閉じるんだぜ
    ↓
ダイオードの配線で文字コードになるんだぜ
    ↓
ラッチに保存するんだぜ
    ↓
タイミング回路が「新しい文字が来たんだぜ」と知らせるんだぜ
```

なんだぜ。

マニュアルには、スイッチのチャタリングを避けるためのレジスタや、1.76kHzのクロックからタイミングを作る回路まで出てくるんだぜ。

今ならマイコンで、

```c
if (key_pressed) {
    send(keycode);
}
```

みたいなことを書くところを、

> **ダイオードとレジスタとゲートの配線そのものがアルゴリズムなんだぜ。**

なんだぜ。

### 昔の端末は、そもそも機械だったんだぜ

もっと昔になると、画面すらないんだぜ。

**Teletype ASR-33** みたいなテレタイプ端末が、コンピュータの入出力装置として普通に使われてたんだぜ。

これはもともと通信網用の機械で、1960年代から70年代にはミニコンの定番端末になったんだぜ。

キーボードから文字を送るんだぜ。

コンピュータから文字が返ってくるんだぜ。

すると紙にガチャガチャ印字するんだぜ。

つまり、

> **ターミナルを開いたら画面が出るんだぜ**

じゃなくて、

> **ターミナルが本当にタイプライターみたいな機械なんだぜ。**

なんだぜ。

IBMもSelectricタイプライターを改造して、**IBM 2741 Terminal** としてコンピュータ端末にしてたんだぜ。

### 「状態機械」を本当に回路で作ってたんだぜ

周辺機器には、

```text
今どの状態なんだぜ？
次に何をするんだぜ？
終わったらどこへ進むんだぜ？
```

という制御が必要なんだぜ。

今ならプログラムで、

```text
STATE_IDLE
STATE_READ
STATE_WRITE
STATE_DONE
```

みたいなstate machineを書くんだぜ。

でもCPUを安く入れられないなら、その状態機械を、

```text
フリップフロップ
カウンタ
レジスタ
論理ゲート
リレー
ダイオード
```

で組むんだぜ。

つまり、

> **if文をゲートで作るんだぜ。**
>
> **変数をレジスタで作るんだぜ。**
>
> **ループをカウンタと配線で作るんだぜ。**

みたいな世界なんだぜ。

プログラムが回路を動かしてるんじゃないんだぜ。

**回路そのものがプログラムみたいなもんなんだぜ。**

### 仕事によってはホスト側が面倒を見るんだぜ

周辺機器側に賢いCPUがいないなら、誰かが細かい仕事をしないといけないんだぜ。

だから昔のシステムでは、

```text
メインCPUが直接面倒を見るんだぜ
専用のI/Oコントローラが面倒を見るんだぜ
別の小型コンピュータに丸投げするんだぜ
```

みたいな構成になるんだぜ。

1964年の **CDC 6600** なんて、中央の高速CPUとは別に **10台のPeripheral Processing Unit** を持っていて、入出力の仕事をそっちへ逃がしてたんだぜ。

つまり、

> **I/Oが面倒だから、I/O専用のコンピュータを10台付けるんだぜ。**

なんだぜ。

豪快なんだぜ。

### そして「端末の回路を1チップにしたいんだぜ」がCPUの歴史につながるんだぜ

ここからがさらに面白いんだぜ。

Computer Terminal Corporationは、端末の回路をもっと小さくしたくて、Intelに1チップのCPUにつながる仕事を依頼したんだぜ。

それが後の **Intel 8008** につながっていくんだぜ。

ただし実際のDatapoint 2200では、そのCPUの完成を待てなかったので、CPU相当の処理を**複数の普通のロジック部品で組んで**製品化したんだぜ。

つまり、

```text
大量の専用ロジックで作ってたんだぜ
        ↓
これ1個のチップにできないんだぜ？
        ↓
マイクロプロセッサの時代なんだぜ
```

という流れがあるんだぜ。

Intel 4004も、登場後は電卓だけじゃなく、周辺機器・端末・制御装置みたいな用途に使えることが重要だったんだぜ。

### もちろん「昔は小さいコンピュータが一切なかった」わけじゃないんだぜ

ここは厳密に言うんだぜ。

1960年代にはもうミニコンもあったんだぜ。

専用の小型コンピュータをI/O制御に使う例もあったんだぜ。

だから、

> **昔の周辺機器には絶対CPUがなかったんだぜ**

ではないんだぜ。

ポイントは、

> **今みたいに数百円以下の小さなプロセッサを、あらゆる機器の中へ気軽に入れられる時代じゃなかったんだぜ。**

## #009 地球シミュレータってな、地球は思ったより広くてシミュレーションしきれなかったんだぜ

2002年、日本に **地球シミュレータ** っていうスーパーコンピュータができたんだぜ。

名前からして強いんだぜ。

> **地球をシミュレーションするんだぜ。**

なんだぜ。

しかもこいつ、完成した当時のLINPACKで **35.86 TFLOPS** を叩き出して、世界最速になったんだぜ。

建物もでかいんだぜ。

計算機を入れる地球シミュレータ棟だけで、およそ

```text
50 m × 65 m × 17 m
```

なんだぜ。

文字どおり、地球を計算するために建物ひとつ用意したんだぜ。

でもな。

**地球は思ったより広かったんだぜ。**

### 地球を計算するには、まず細かく切るんだぜ

コンピュータの中に本物の地球を入れることはできないんだぜ。

だから大気を、

```text
この場所の気温はいくつなんだぜ
風速はいくつなんだぜ
気圧はいくつなんだぜ
水蒸気はいくつなんだぜ
```

みたいな格子に区切って計算するんだぜ。

例えば100kmメッシュなら、

> **地球を100kmくらいのマス目に切って考えるんだぜ。**

という感じなんだぜ。

でも100kmのマスの中には、

```text
山があるんだぜ
海岸線があるんだぜ
積乱雲があるんだぜ
雨が降ってる場所と降ってない場所があるんだぜ
```

なんだぜ。

当然、全部は見えないんだぜ。

### 雲を直接計算したかったんだぜ

当時の全球気候モデルでは、格子より小さい雲の動きをそのまま全部計算できなかったんだぜ。

だから、

> **この条件なら、このくらい雲ができたことにするんだぜ。**

みたいな **パラメタリゼーション** で近似してたんだぜ。

そこで地球シミュレータを使って開発されたのが **NICAM** なんだぜ。

こいつは地球全体を細かい格子で覆って、雲の集団をもっと直接計算しようとしたんだぜ。

最終的には、

```text
全球
3.5 kmメッシュ
鉛直54層
時間刻み15秒
```

なんて計算をやったんだぜ。

2005年には、3.5kmメッシュで全球の雲を解像するシミュレーションに世界で初めて成功したんだぜ。

だから、

> **地球シミュレータは地球をシミュレーションできなかったんだぜ。**

は、そのままだと嘘なんだぜ。

ちゃんとできたんだぜ。

でも問題はここからなんだぜ。

### 3.5kmでも地球全体にすると、とんでもない数になるんだぜ

NICAMは正20面体をどんどん細かく分割して地球を覆うんだぜ。

3.5km級の格子では、水平だけでおよそ **4,200万地点** になるんだぜ。

それを鉛直54層にすると、単純に場所だけ数えても **20億を超える格子点×層** になるんだぜ。

しかも各場所で一個の数字だけ計算するわけじゃないんだぜ。

```text
風なんだぜ
温度なんだぜ
圧力なんだぜ
水蒸気なんだぜ
雲水なんだぜ
氷なんだぜ
```

みたいな変数を何個も持つんだぜ。

そして3.5km実験の時間刻みは **15秒** なんだぜ。

地球の1日は86,400秒だから、

```text
86,400 ÷ 15 = 5,760回
```

も時間を進めないと、シミュレーション上の1日が終わらないんだぜ。

**地球、広すぎるんだぜ。**

### 世界一のスパコンでも、地球の1日に何時間もかかったんだぜ

地球シミュレータ上の開発報告では、3.5kmメッシュで物理過程まで入れた全球計算は、

> **地球の1日分を計算するのに、およそ2〜3時間かかるんだぜ。**

と見積もられていたんだぜ。

つまり未来を1日見るために、現実時間で数時間使うんだぜ。

1年やろうとしたら、単純計算でもかなり重いんだぜ。

しかも2005年の全球雲解像実験の論文では、

> **計算資源の制約で1か月より長く積分できなかったんだぜ。**

と書かれてるんだぜ。

そして研究者自身が、

> **それじゃ気候や季節変化を調べるには短すぎるんだぜ。**

としてるんだぜ。

世界一のスーパーコンピュータを作ったんだぜ。

地球全体も計算できたんだぜ。

でも、

> **じゃあその高解像度の地球を何年分も回すんだぜ。**

となると無理だったんだぜ。

### しかも3.5kmでも「本物の地球」じゃないんだぜ

ここがさらに恐ろしいところなんだぜ。

3.5kmメッシュって、当時としてはとんでもなく細かいんだぜ。

でも本物の雲の中では、

```text
数kmなんだぜ
数百mなんだぜ
数mなんだぜ
数mmの水滴なんだぜ
もっと小さい分子なんだぜ
```

まで現象が続いてるんだぜ。

つまり3.5kmまで細かくして、

> **めちゃくちゃ細かい地球なんだぜ。**

と思っても、本物から見たらまだ巨大なマス目なんだぜ。

地球を完全にシミュレーションしようと思ったら、

**細かくすればするほど計算量が爆発するんだぜ。**

### 地球シミュレータの本当に面白いところなんだぜ

だから地球シミュレータの話は、

> **世界一のコンピュータで地球を完全再現したんだぜ。**

という話じゃないんだぜ。

むしろ、

> **世界一のコンピュータを作って地球を計算してみたら、それでも地球はデカすぎたんだぜ。**

という話なんだぜ。

もちろん、それまでできなかった3.5km全球雲解像計算を実現したのは、とんでもない成果なんだぜ。

でも同時に、

**計算機を速くすれば自然を全部そのまま計算できる、というほど現実世界は小さくないんだぜ。**

というのも見えてきたんだぜ。

地球シミュレータって名前なのに、

**地球の大きさを思い知らされるコンピュータだったんだぜ。**

## #010 文字ってな、1文字＝1文字コードじゃないんだぜ

プログラムを始めると、

```text
"A" は1文字なんだぜ
"B" も1文字なんだぜ
"あ" も1文字なんだぜ
```

って感覚になるんだぜ。

だから、

> **画面に1文字見えてるなら、コンピュータの中でも1個の文字データなんだぜ。**

と思いがちなんだぜ。

でもな。

**Unicodeの世界では「1文字」って、何を1文字と呼んでるのかで答えが変わるんだぜ。**

### 同じ「é」なのに中身が違うことがあるんだぜ

例えばこの文字なんだぜ。

```text
é
```

こいつは、

```text
U+00E9  LATIN SMALL LETTER E WITH ACUTE
```

という **1個のコードポイント** で表せるんだぜ。

でも同じ見た目を、

```text
U+0065  e
U+0301  COMBINING ACUTE ACCENT
```

という **2個のコードポイント** でも作れるんだぜ。

つまり、

```text
é
```

と見えていても、中身が

```text
[é]
```

の場合と、

```text
[e][ ́]
```

の場合があるんだぜ。

人間の目にはほぼ同じ1文字なんだぜ。

でもコンピュータから見ると、同じ並びとは限らないんだぜ。

だからUnicodeには **正規化（Normalization）** なんて話まで出てくるんだぜ。

### 絵文字になるともっとひどいんだぜ

例えばこれなんだぜ。

```text
👨‍👩‍👧‍👦
```

見た目は **家族の絵文字1個** なんだぜ。

でも中では、

```text
👨
ZWJ
👩
ZWJ
👧
ZWJ
👦
```

という並びなんだぜ。

ZWJは **ZERO WIDTH JOINER** なんだぜ。

ざっくり言えば、

> **この絵文字と次の絵文字をくっつけて1個っぽく表示してくれなんだぜ。**

という文字なんだぜ。

つまり画面では1個でも、内部では複数のUnicodeコードポイントなんだぜ。

Unicode自身も、ZWJ sequenceは内部的には文字の列なのに、利用者からは1個の絵文字のように振る舞うとしてるんだぜ。

### JavaScriptで数えると事故るんだぜ

ここでJavaScriptなんだぜ。

```javascript
"abc".length
```

は、

```text
3
```

なんだぜ。

まあ普通なんだぜ。

でも、

```javascript
"😀".length
```

は、

```text
2
```

なんだぜ。

1個に見えるのに2なんだぜ。

さらに、

```javascript
"👨‍👩‍👧‍👦".length
```

は、

```text
11
```

なんだぜ。

**1文字に見えるものを数えたら11なんだぜ。**

意味が分からないんだぜ。

### JavaScriptのlengthは「文字数」を数えてないんだぜ

理由はJavaScriptの文字列が **UTF-16** で扱われるからなんだぜ。

JavaScriptの `.length` が数えてるのは、

> **人間が見ている文字数なんだぜ**

じゃなくて、

> **UTF-16のコード単位が何個あるんだぜ**

なんだぜ。

だから、

```text
"A"
```

みたいな文字なら1コード単位なんだぜ。

でも、

```text
😀
```

みたいなBMPの外にある文字は、UTF-16では **サロゲートペア** という2コード単位になるんだぜ。

なので、

```javascript
"😀".length === 2
```

になるんだぜ。

### じゃあArray.fromなら解決なんだぜ？

そこで、

```javascript
Array.from("😀").length
```

なら、

```text
1
```

になるんだぜ。

いい感じなんだぜ。

でも、

```javascript
Array.from("👨‍👩‍👧‍👦").length
```

は、

```text
7
```

なんだぜ。

まだ1じゃないんだぜ。

なぜなら `Array.from` はUnicodeの **コードポイント** 単位ではかなりマシに扱えるけど、

> **人間が見て1文字なんだぜ**

という単位までは数えてないからなんだぜ。

家族絵文字は、

```text
👨 + ZWJ + 👩 + ZWJ + 👧 + ZWJ + 👦
```

の7コードポイントなんだぜ。

### 人間が思う「1文字」に近いものには名前があるんだぜ

Unicodeでは、人間がだいたい「これで1文字なんだぜ」と感じるまとまりに近い概念として **grapheme cluster** があるんだぜ。

ざっくり整理すると、

```text
glyph
    画面に描かれる形なんだぜ

grapheme cluster
    人間が1文字っぽく感じる単位なんだぜ

code point
    Unicode上の番号なんだぜ

code unit
    UTF-8やUTF-16みたいな符号化方式での単位なんだぜ
```

なんだぜ。

こいつらは全部同じじゃないんだぜ。

ここが文字列処理の沼の入口なんだぜ。

### JavaScriptでも「見た目の文字」で分けられるんだぜ

今のJavaScriptなら `Intl.Segmenter` を使ってgrapheme単位に分割できるんだぜ。

```javascript
const segmenter = new Intl.Segmenter("ja", {
    granularity: "grapheme"
});

const chars = [...segmenter.segment("👨‍👩‍👧‍👦")];

console.log(chars.length);
```

なら、

```text
1
```

になるんだぜ。

ようやく人間の感覚に近づいたんだぜ。

### 国旗も1文字じゃないんだぜ

例えば、

```text
🇯🇵
```

なんだぜ。

見た目は日本国旗1個なんだぜ。

でもこれは **REGIONAL INDICATOR SYMBOL LETTER J** と **REGIONAL INDICATOR SYMBOL LETTER P** の2コードポイントの組み合わせなんだぜ。

JavaScriptではそれぞれがサロゲートペアになるので、

```javascript
"🇯🇵".length
```

は、

```text
4
```

なんだぜ。

旗1個なのに4なんだぜ。

### だから文字数制限は意外と難しいんだぜ

例えばSNSを作って、

> **名前は10文字までなんだぜ。**

としたいんだぜ。

じゃあ何を10個までにするんだぜ。

```text
10バイトなんだぜ？
10 UTF-16コード単位なんだぜ？
10コードポイントなんだぜ？
10 grapheme clusterなんだぜ？
```

全部結果が違う可能性があるんだぜ。

「文字数を数える」って聞くと小学生でも分かりそうな処理なんだぜ。

でもコンピュータで真面目にやると、

**そもそも文字とは何なんだぜ**

から始まるんだぜ。

### だからなんだぜ

画面に、

```text
👨‍👩‍👧‍👦
```

が1個見えてるんだぜ。

人間は、

> **1文字なんだぜ。**

と思うんだぜ。

Unicodeは、

> **複数のコードポイントからなるgrapheme clusterなんだぜ。**

と言うんだぜ。

JavaScriptの `.length` は、

> **11なんだぜ。**

と言うんだぜ。

全員違うんだぜ。

だから、

> **1文字＝1文字コードなんだぜ**

は、ASCIIくらいの世界では気持ちよく成り立つんだけど、

**Unicodeの世界に出た瞬間、だいたい壊れるんだぜ。**

## #011 TCPってな、メッセージを送ってるわけじゃないんだぜ

ネットワークプログラムを書き始めると、こんなコードを書くんだぜ。

```python
sock.send(b"HELLO")
sock.send(b"WORLD")
```

すると気分としては、

```text
HELLO というメッセージを送るんだぜ
WORLD というメッセージを送るんだぜ
```

なんだぜ。

だから受信側でも、

```python
a = sock.recv(1024)
b = sock.recv(1024)
```

とやれば、

```text
a = HELLO
b = WORLD
```

になる気がするんだぜ。

でもな。

**TCPはそんな約束をしてないんだぜ。**

### TCPが運んでるのは「メッセージ」じゃなくてバイト列なんだぜ

TCPの仕様では、TCPはアプリケーションに対して **reliable, in-order, byte-stream service** を提供するんだぜ。

つまり、

```text
順番どおりなんだぜ
途中で消えたら再送するんだぜ
でも区切りは知らないんだぜ
```

なんだぜ。

TCPからすると、

```text
HELLO
WORLD
```

じゃなくて、

```text
HELLOWORLD
```

という **10バイトの流れ** なんだぜ。

どこで `send()` を呼んだかなんて、受信側にそのまま伝える義務はないんだぜ。

### sendを2回してもrecvが2回とは限らないんだぜ

送信側が、

```python
sock.sendall(b"HELLO")
sock.sendall(b"WORLD")
```

としたとしても、受信側では例えば、

```text
recv() → HELLOWORLD
```

と一発で来ることもあるんだぜ。

逆に、

```text
recv() → HE
recv() → LLO
recv() → WOR
recv() → LD
```

みたいに細切れになることもあるんだぜ。

あるいは、

```text
recv() → HELLOW
recv() → ORLD
```

なんて区切りもあり得るんだぜ。

**送ったときの区切りと、受け取るときの区切りには対応関係がないんだぜ。**

RFC 9293にも、アプリケーションのread/write bufferの境界とTCP segmentの境界には相関を保証しない、と明記されてるんだぜ。

### TCPパケットの境界すら、アプリから見たメッセージ境界じゃないんだぜ

ここで、

> **じゃあTCPパケット1個を1メッセージだと思えばいいんだぜ？**

となりそうなんだぜ。

それも違うんだぜ。

TCPは内部ではデータを **segment** に分けてネットワークへ流すんだぜ。

でもsegmentをどう切るかは、

```text
MSSなんだぜ
輻輳制御なんだぜ
送信バッファなんだぜ
Nagleなんだぜ
OSの都合なんだぜ
ネットワークの都合なんだぜ
```

みたいな要因で変わるんだぜ。

アプリケーションが、

```text
ここからここまでが1個のメッセージなんだぜ
```

と思っていても、TCP自身は知らないんだぜ。

**TCP segmentはアプリケーションのメッセージじゃないんだぜ。**

### じゃあメッセージの区切りは誰が決めるんだぜ

**アプリケーション側なんだぜ。**

例えばHTTP/1.xなら、

```text
Content-Length: 123
```

みたいに長さを書くんだぜ。

あるいは改行で区切るプロトコルなら、

```text
HELLO\n
WORLD\n
```

みたいにするんだぜ。

他にも、

```text
最初の4バイトに長さを書くんだぜ
そのあとに本体を書くんだぜ
```

みたいな **length prefix** を使うんだぜ。

例えば、

```text
[0005][HELLO][0005][WORLD]
```

みたいな感じなんだぜ。

つまりTCPの上でメッセージ通信をしたいなら、

> **どこまでが1メッセージなのかを、自分たちで決めるんだぜ。**

なんだぜ。

### だからrecv(1024)は「1024バイト受け取る」じゃないんだぜ

これも初心者がハマるところなんだぜ。

```python
data = sock.recv(1024)
```

を見ると、

> **1024バイト受信するんだぜ。**

に見えるんだぜ。

でも普通は、

> **最大1024バイトまで受け取るんだぜ。**

なんだぜ。

今受信バッファに30バイトしか来てなければ、30バイトで返ることがあるんだぜ。

だから、

```python
header = sock.recv(100)
```

として、

> **100バイトのヘッダが取れたんだぜ。**

と思ったら事故るんだぜ。

必要なバイト数が決まっているなら、足りるまで繰り返して読む必要があるんだぜ。

### 送る側も一発で全部送れるとは限らないんだぜ

低レベルな `send()` は、

```text
渡したデータを全部送ったんだぜ
```

とは限らないんだぜ。

一部だけ送って、

```text
ここまでは受け取ったんだぜ
残りはまた呼んでくれなんだぜ
```

になることがあるんだぜ。

だからPythonには `sendall()` があるし、他の言語やAPIでも「全部書けるまでループする」処理が必要になることがあるんだぜ。

ここでもTCPは、

**メッセージ単位じゃなくて、バイトの流れなんだぜ。**

が効いてくるんだぜ。

### UDPはこの点では話が違うんだぜ

UDPは **datagram** を送るんだぜ。

つまり送信側が1個のdatagramとして送ったものは、受信側でも1個のdatagramとして扱われるんだぜ。

TCPみたいに、

```text
HELLO + WORLD
```

が勝手に、

```text
HELLOWORLD
```

という一続きのストリームになるわけじゃないんだぜ。

もちろんUDPには、

```text
届かないかもしれないんだぜ
順番が変わるかもしれないんだぜ
重複するかもしれないんだぜ
```

という別の問題があるんだぜ。

だから、

```text
TCP = 信頼できるバイトストリームなんだぜ
UDP = メッセージ境界を持つdatagramなんだぜ
```

くらいに見ると違いが分かりやすいんだぜ。

### だからなんだぜ

TCPで、

```text
send("HELLO")
send("WORLD")
```

したんだぜ。

人間は、

> **2個のメッセージを送ったんだぜ。**

と思うんだぜ。

TCPは、

> **10バイト預かったんだぜ。順番どおり届けるんだぜ。区切り？ 知らないんだぜ。**

なんだぜ。

ここを知らないと、

```text
たまにJSONが途中で切れるんだぜ
たまに2個のJSONがくっつくんだぜ
ローカルでは動くのに本番で壊れるんだぜ
```

みたいなネットワークバグになるんだぜ。

**TCPはメッセージ配送サービスじゃないんだぜ。**

**順番のある、信頼できるバイトの川なんだぜ。**

## #013 同じことを書くにも、速さは全然違うんだぜ

プログラムを書いてると、

```text
動けば同じなんだぜ
```

に見えるコードがあるんだぜ。

でもな。

**同じ結果を出すコードでも、書き方やデータ構造で速度が何倍も何百倍も変わることがあるんだぜ。**

今回はこの環境の **CPython 3.13.5** で `timeit` を使って測った一例なんだぜ。

数字はCPUやPythonのバージョン、入力サイズで変わるんだぜ。

だから、

> **この倍率が世界共通なんだぜ。**

ではないんだぜ。

でも、

> **同じ意味でも、実装の仕方でこんなに差が出るんだぜ。**

を見るには十分なんだぜ。

### 足し算するなら、手で回すよりsumの方が速かったんだぜ

10万個の整数を足すんだぜ。

まず普通に書くんだぜ。

```python
s = 0

for i in range(100_000):
    s += i
```

この環境では、だいたい **3.88 ms** だったんだぜ。

一方で、

```python
sum(range(100_000))
```

なら、だいたい **1.55 ms** だったんだぜ。

つまり手書きループの方が、

> **約2.5倍遅かったんだぜ。**

なんだぜ。

どっちもやってることは、

```text
0から99999まで足すんだぜ
```

なんだぜ。

でもPython側で何度もループを回すより、組み込み関数にまとめて仕事を渡した方が速くなることがあるんだぜ。

しかも、

```python
sum(values)
```

の方が何をしたいかも一発で分かるんだぜ。

**速くて短いこともあるんだぜ。**

### 文字列をつなぐならjoinが10倍くらい速かったんだぜ

1万個の文字列をつなぐんだぜ。

こう書けるんだぜ。

```python
s = ""

for part in parts:
    s += part
```

この環境では、だいたい **0.589 ms** だったんだぜ。

でも、

```python
"".join(parts)
```

なら、だいたい **0.056 ms** だったんだぜ。

つまり `+=` で繰り返しつなぐ方が、

> **約10.4倍遅かったんだぜ。**

なんだぜ。

これも結果は同じ文字列なんだぜ。

でも `join` は、

> **最初から全部まとめてつなぐ仕事なんだぜ。**

と処理系に伝えられるんだぜ。

「何をしたいか」を高いレベルで書いた方が、処理系が効率よくやれることもあるんだぜ。

### 探すだけで2700倍くらい差が出たんだぜ

今度は、

```text
0から9999まで入ったデータから9999を探すんだぜ
```

をやるんだぜ。

listなら、

```python
xs = list(range(10_000))

9999 in xs
```

なんだぜ。

この環境では1回あたり、だいたい **58.6 μs** だったんだぜ。

一方でsetなら、

```python
xs = set(range(10_000))

9999 in xs
```

は、だいたい **0.021 μs** だったんだぜ。

この実測ではlistの検索が、

> **約2700倍遅かったんだぜ。**

なんだぜ。

急に桁がおかしいんだぜ。

理由は単純なんだぜ。

listは基本的に、

```text
これなんだぜ？
違うんだぜ
次なんだぜ？
違うんだぜ
次なんだぜ？
...
```

と順番に探すんだぜ。

setはハッシュを使って、

> **たぶんこの辺にあるんだぜ。**

とかなり直接的に探しに行けるんだぜ。

**アルゴリズムやデータ構造の違いは、細かい書き方の工夫なんか吹き飛ばすことがあるんだぜ。**

### じゃあ全部setにすればいいんだぜ？

そうはならないんだぜ。

setには、

```text
重複を持たないんだぜ
インデックスで何番目とは取れないんだぜ
listとは意味が違うんだぜ
追加のメモリも使うんだぜ
```

という性質があるんだぜ。

しかも今回の測定では、**setを作る時間は検索時間に含めてない**んだぜ。

1回しか検索しないのに、

```python
9999 in set(xs)
```

と毎回setを作ってたら、その準備の方が高くつくこともあるんだぜ。

つまり、

> **検索だけ見たら2700倍速いんだぜ。**

と、

> **プログラム全体が2700倍速くなるんだぜ。**

は全然違う話なんだぜ。

### ベンチマークの数字だけ見ると簡単に騙されるんだぜ

例えば、

```text
AはBより10倍速いんだぜ
```

と言われると、Bを全部書き換えたくなるんだぜ。

でも元の処理が、

```text
1回 0.05 ms
```

しか使ってないなら、10倍速くしても体感できないかもしれないんだぜ。

逆に、

```text
毎秒100万回呼ばれるんだぜ
```

なら、小さな差でも巨大になるんだぜ。

大事なのは、

```text
何回呼ばれるんだぜ
どれくらいのデータなんだぜ
全体時間の何％なんだぜ
メモリはどれくらい増えるんだぜ
コードは読みにくくならないんだぜ
```

なんだぜ。

### 読みやすいコードを壊して1μsを取りに行くこともできるんだぜ

例えば、

```python
result = some_clear_function(data)
```

を、

```text
関数呼び出しを消すんだぜ
変数を使い回すんだぜ
条件分岐を展開するんだぜ
読みにくい最適化を山ほど入れるんだぜ
```

にすれば少し速くなることはあるんだぜ。

でも半年後、

> **これ何してるんだぜ？**

となったら、人間の時間を大量に失うんだぜ。

コンピュータの1ミリ秒を救うために、

**プログラマの1時間を燃やしたら得なのか**

は考えないといけないんだぜ。

### まず測るんだぜ

だから速度が気になったら、

> **たぶんここが遅いんだぜ。**

で書き換え始めるんじゃないんだぜ。

まず測るんだぜ。

Pythonなら `timeit` みたいな道具があるんだぜ。

本物のアプリならprofilerを使って、

```text
本当に遅い場所はどこなんだぜ
```

を見るんだぜ。

速くするなら、

**一番時間を食ってるところからなんだぜ。**

### だからなんだぜ

コードには、

```text
実行速度なんだぜ
メモリ使用量なんだぜ
読みやすさなんだぜ
書きやすさなんだぜ
保守しやすさなんだぜ
バグりにくさなんだぜ
```

があるんだぜ。

速度は大事なんだぜ。

遅すぎたら使い物にならないんだぜ。

でも、

> **一番速いコードが、一番いいコードなんだぜ。**

とは限らないんだぜ。

必要なだけ速くて、意味が分かって、壊しにくい。

その方がいい場面はいくらでもあるんだぜ。

**早ければいいってもんじゃないぜ。**
