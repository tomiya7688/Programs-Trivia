# GitHub Actionsのpull_request_target、12月から既定で止まるんだぜ！

- **掲載日**: 2026-11-03
- **発表日**: 2026-11-02
- **適用予定日**: 2026-12-02
- **区分**: Tech News / GitHub Actions / セキュリティ
- **対象**: GitHub.comの公開リポジトリ

## 「PRが来たら動くはずのCI」が止まるんだぜ！？

GitHubが2026年11月2日、**公開リポジトリでは`pull_request_target`イベントを12月2日から既定でブロックする**と発表したんだぜ。

「えっ、Pull Requestのチェックが全部止まるんだぜ！？」と思うかもしれないけど、そこは違うんだぜ。

止める対象は**`pull_request_target`という特定のイベント**なんだぜ。普通の`pull_request`イベントや、ほかのGitHub Actionsをまとめて禁止する話ではないんだぜ。

もともと11月2日に強制適用する予定だったけど、12月2日へ延期されたんだぜ。

## `pull_request`と`pull_request_target`、似てるけど危なさが違うんだぜ

名前は似ているけど、実行する文脈が違うんだぜ。

~~~yaml
on:
  pull_request_target:
~~~

`pull_request_target`は、**PRの送り先（ベース）リポジトリの文脈で実行される**んだぜ。必要な権限を与えられたジョブなら、シークレットなどを利用できる場合もあるんだぜ。

このイベント自体が自動的に外部PRのコードを実行するわけではないぜ。

でも、外部フォークから来たPRの内容をチェックアウトして、そのままビルドやスクリプトを走らせたらどうなるんだぜ？

~~~text
外部PRが来るんだぜ
    ↓
高い権限のワークフローが動くんだぜ
    ↓
信頼できないコードまで実行したら……
    ↓
シークレットやCI環境を危険にさらすんだぜ！
~~~

**便利なトリガーと安全なコード実行は別問題**なんだぜ。GitHubが既定の保護を強めるのはこのためなんだぜ。

## 12月まで何も起きないわけじゃないんだぜ

GitHubは本格適用の前に、**brownout（短時間だけ強制ブロックする試験期間）**を2回予定しているんだぜ。

| 日付（UTC） | 日本時間（JST） |
| --- | --- |
| 11月9日 16:00〜18:00 | 11月10日 01:00〜03:00 |
| 11月16日 16:00〜18:00 | 11月17日 01:00〜03:00 |

この時間帯に既定ルールでブロックされた実行は、失敗扱いのrunとエラー注釈が記録されるんだぜ。**ワークフロー本体は実行されない**んだぜ。

試験期間が終わると、12月2日まで既定ルールは評価モードに戻り、警告によって影響を把握できる予定なんだぜ。

## 対応を間違えて、保護を全部解除したら本末転倒なんだぜ

GitHubの案内では、まず**Insightsでブロック対象になりそうなワークフローを確認**するんだぜ。

必要ないならそのまま保護するんだぜ。必要なら、適用される**Actionsイベントポリシーで明示的に許可**できるんだぜ。許可を広げすぎず、ワークフローファイルを指定して対象を限定できるぜ。

ただし、許可すれば危険なコードが安全になるわけではないんだぜ。外部PRのコードを高権限で実行しない設計も別に必要なんだぜ。

今回の対象はGitHub Free、Team、Enterprise Cloud上の**公開リポジトリ**なんだぜ。非公開・内部リポジトリ、およびGitHub Enterprise Serverはこの新しい既定ルールの対象外なんだぜ。

## だからなんだぜ

**12月2日にCIが壊れてから慌てるより、11月の試験期間までに確認するんだぜ！**

セキュリティは「全部禁止」だけでも「全部許可」だけでも済まないんだぜ。イベントを使う理由と、そこで何を実行するかを分けて考えるニュースなんだぜ。
