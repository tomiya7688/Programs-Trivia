# News — 新しい技術の話も「なんだぜ」で届けるんだぜ！

Programs-Triviaはトリビアだけじゃないんだぜ。
技術の新しい出来事、GitHubで注目を集めるリポジトリ、Tomiya製プロジェクトのリリースも記録していくんだぜ。

読んで面白いことと、事実が正しいことは両立するんだぜ。
**口調はゆるくても、日付・内容・出典はまじめに扱うんだぜ。**

## 事故でも脆弱性でも、この口調で行くんだぜ

ニュースが重大だからって、急にお堅い記者会見の文章にはしないんだぜ。

**「これは大変だぜ！」「おいおい、そこが壊れるのかよ！」「まさか守る側が止めるとはな！」** くらいの勢いで行くんだぜ。歴史を振り返ると、いまでは思わず笑っちゃうような大事故もあるんだぜ。

ツッコミや軽い煽りを入れていいのは、仕様の穴、壊れた仕組み、謎の運用、過信していた設計なんだぜ。**被害者の苦労を茶化したり、被害や攻撃を確認なしに盛ったりはしない**んだぜ。

深刻さと文体は別なんだぜ。被害の有無、影響範囲、発見と悪用の区別、対応策はちゃんと書くぜ。**トリビアもニュースも、同じTrivaのノリなんだぜ！**

セキュリティソフトも、特定メーカーの宣伝や「これ一択！」にはしないんだぜ。OS標準の防御でも十分な場合があるし、運用によって追加機能が必要な場合もあるんだぜ。万能な製品はないから、更新、バックアップ、認証対策、誤検知や相性まで含めて扱うぜ。セキュリティ製品自身の事故も、必要なら笑えるツッコミと一緒に紹介するんだぜ。

## ファイル名も日本語にするんだぜ

ニュースは `news/YYYY/MM/カテゴリ/YYYY-MM-DD-日本語の短い題名.md`、トリビアは `trivia/NNN-日本語の短い題名.md` にするんだぜ。ニュースの年月は**掲載日**で決めるぜ。番号と日付は並べ替えに残すんだぜ。

製品名、CVE番号、バージョンは英数字でもいいんだぜ。URLで扱いにくい `/`、`?`、`#`、空白はファイル名から外すぜ。

過去に共有した英語ファイル名のURLには、移動先を案内する短い文書を残しているぜ。**新しいリンクは日本語ファイル名の正本へ張るんだぜ。** GitHub慣例の `README.md` と `TEMPLATE.md` は例外なんだぜ。

## ニュースを書くときの約束なんだぜ

1. **一次情報を確認するんだぜ。** 公式リリースノート、公式ブログ、元のGitHubリポジトリを優先するぜ。
2. **公開日と出来事の日付を分けるんだぜ。** あとから過去のニュースを書くこともあるからなんだぜ。
3. **何ができるかと、まだできないことを両方書くんだぜ。** とくに実験的な技術を完成扱いしないんだぜ。
4. **GitHubのStar数やTrending順位は変動するんだぜ。** 必要なら観測日と確認元を明記し、数字を盛らないぜ。
   注目リポジトリの記事には、確認日と掲載を確認した一覧を記録するんだぜ。公式資料で紹介した内容と、自分で試した結果も区別するぜ。
5. **Tomiya自身のプロジェクトはその関係を明記するんだぜ。** 外部のニュースと区別するぜ。
6. **ソースコード、素材、商標にはライセンスがあるんだぜ。** 紹介と転載は別物なんだぜ。
7. **口調は「〜だぜ」「〜なんだぜ」、重大ニュースでも変えないんだぜ。** これは大変だぜ！ でも事実はちゃんと検証して、間違いが分かったら訂正するぜ。
8. **変な事故にはツッコミを入れるんだぜ。** 技術の皮肉や雑な運用を軽く煽るのは歓迎だぜ。ただし、被害者じゃなくて仕組みにツッコむんだぜ。
9. **セキュリティソフトを持ち上げすぎないんだぜ。** 個別製品の広告にしないぜ。防御の一層として、更新やバックアップ、誤検知や導入負荷も含めて紹介するんだぜ。

記事の雛形は[テンプレート](TEMPLATE.md)を使えるんだぜ。
